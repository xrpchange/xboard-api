# Поток верификации email при создании эскроу-токена

**Цель:** перед созданием эскроу-токена отправлять код подтверждения на первый доступный email из настроенных в приложении, затем сканировать этот ящик (включая Spam/Junk) встроенным почтовым клиентом и находить код. Только после успешной верификации разрешать создание токена.

**Статус:** проектирование интерфейса и потока. Реализация — после согласования.

---

## 1. Участники и данные

| Компонент | Роль |
|-----------|------|
| **Настроенные email (Settings)** | Список подключённых аккаунтов (EmailAccountStorage). Берём **первый** по порядку как целевой для кода. |
| **API (xboard-api)** | Генерация кода, отправка письма с кодом на указанный email, приём кода при создании токена (или отдельный шаг confirm). |
| **Клиент (встроенный почтовый клиент)** | IMAP/POP3: сканирование папок выбранного ящика (INBOX + Spam/Junk и аналог), поиск письма с кодом, извлечение кода. |
| **Экран создания токена** | Пошаговый флоу: выбор крипты → запрос кода → ожидание/сканирование → ввод кода (fallback) → создание токена. |

---

## 2. Папки для сканирования (Spam и аналоги)

Почтовые клиенты и провайдеры по-разному называют папку «спам». Нужно сканировать не только INBOX.

**Типичные имена папок (IMAP):**

| Папка | Провайдеры |
|-------|-------------|
| INBOX | Все |
| Spam | Yandex, многие |
| Junk | Outlook, Apple |
| Junk E-mail | Outlook (англ.) |
| Junk Email | Вариант |
| [Gmail]/Spam | Gmail (полное имя) |
| Bulk | Некоторые |
| Bulk Mail | Некоторые |
| &BCEEPwQwBDw- (Junk в UTF-7) | Старые серверы |

**Подход:**

1. **Либо** при сканировании запрашивать список папок у сервера (IMAP `LIST`/`LSUB`), затем для каждой папки из списка «подозрительных» (по имени: spam, junk, bulk и т.п.) + INBOX — получать список писем и искать код.
2. **Либо** задать фиксированный список имён папок для открытия: `INBOX`, `Spam`, `Junk`, `Junk E-mail`, `Junk Email`, `[Gmail]/Spam`, `Bulk` — и открывать только те, что существуют у данного аккаунта.

Рекомендация: **сначала** попробовать открыть папки по фиксированному списку имён; при необходимости добавить получение списка папок (ClientEmailReader или отдельный метод) и фильтрацию по имени.

**POP3:** обычно только INBOX; папка Spam часто недоступна по POP3. В этом случае сканируем только INBOX и показываем подсказку «Проверьте папку Спам вручную» при таймауте.

## 3. API (xboard-api)

### 3.1. Вариант A: два шага (request-code → create с code)

1. **POST /v1/escrow-tokens/request-verification-code**  
   - Body: `email`, puzzle fields, опционально `batch_size`; **опционально локализованные фрагменты письма** с клиента: `mail_subject`, `mail_header`, `mail_intro`, `mail_after_code`, `mail_footer` — API только подставляет в шаблон (см. `MailboxVerificationCodeMail`, view `mailbox_verification_code_*`). Если `mail_subject`+`mail_intro` не переданы, используется **legacy English** текст.  
   - Проверки: proof-of-work puzzle, email из разрешённого провайдера, rate limit.  
   - Действия: сгенерировать код (например 6 цифр), сохранить в кэш с TTL, отправить **multipart text+HTML** на `email`.  
   - Ответ: `{ "success": true, "expires_in_minutes": 30 }` или ошибка.

2. **POST /v1/escrow-tokens/create** (текущий, расширить)  
   - Body: добавить опциональное поле `verification_code`.  
   - Если код обязателен для создания: проверить код по email (из кэша), при совпадении — удалить код из кэша и вызвать Core (create token). Иначе 401/403.

### 3.2. Вариант B: один шаг (create с предварительной отправкой кода)

- Клиент сначала вызывает **request-verification-code**, затем сканирует почту, получает код, затем вызывает **create** с параметром `verification_code`.  
- Логика та же, что в A; различие только в том, как клиент комбинирует вызовы.

Рекомендация: **вариант A** — явный шаг «запросить код» и отдельный шаг «создать токен с кодом». Так проще логировать и тестировать.

### 3.3. Хранение кода на сервере

- Ключ: `email` (или `email + intent: escrow_token_create`).  
- Значение: код (строка), время истечения.  
- Хранилище: Redis или кэш Laravel (Cache::put с TTL). При проверке в create: Cache::get, сравнение, при успехе Cache::forget.

## 4. Клиент (xboard-client)

### 4.1. Выбор email для кода

- Источник: `EmailAccountStorage.getEmailAccounts()`.  
- Правило: **первый** элемент списка (индекс 0). Если список пуст — показать экран/сообщение «Добавьте email в Настройках».  
- Не давать пользователю выбирать ящик на этом шаге (по ТЗ — «первый доступный»). При желании позже можно добавить выбор.

### 4.2. Расширение ClientEmailReader (папки)

Сейчас: только INBOX, фиксированно.

Нужно одно из двух:

- **Вариант 1.** Добавить метод вида `getEmailListFromFolders(account, folderNames, limit, offset)` — для каждого имени папки из `folderNames` открывать папку (если есть), забирать список писем, объединять, сортировать по дате, возвращать с указанием папки (чтобы потом запросить raw по messageId в контексте папки).  
- **Вариант 2.** Добавить `listFolders(account): List<String>` и `getEmailList(account, folderName, limit, offset)`. UI/логика по очереди запрашивает INBOX, затем папки с именами из списка (Spam, Junk, …).

Для поиска кода достаточно **варианта 2**: список папок опционален; вызываем `getEmailList(account, "INBOX", ...)`, затем `getEmailList(account, "Spam", ...)` и т.д. по фиксированному списку имён. Если папка не существует — сервер/библиотека вернёт ошибку, пропускаем.

Изменить контракт:

- `getEmailList(account, limit, offset)` → оставить как вызов по умолчанию для INBOX.  
- Добавить перегрузку или новый метод: `getEmailList(account, folderName: String, limit, offset)` и по возможности `getRawEmail(account, folderName: String, messageId: String)` если номера сообщений не уникальны между папками.  
- В JavaMail: для другой папки использовать `store.getFolder(folderName)` вместо `getFolder("INBOX")`.

### 4.3. Поиск кода в письмах

- Текущий текст письма: произвольный (локализованный); тело содержит **строку из шести цифр** (отдельной строкой) или строку вида «… creation: 123456» — см. клиентский `EscrowVerificationCode`.
- Алгоритм: для каждой папки запросить последние N писем (например 20), по каждому при необходимости запросить raw/body (или subject + snippet), искать по регулярному выражению (код из 5–8 цифр или конкретный формат от бэкенда).  
- Как только код найден — вернуть его и прекратить сканирование.  
- Ограничение по времени: например 5 минут ожидания, затем предложить «Ввести код вручную».

### 4.4. UI (экран создания токена)

Предлагаемая последовательность шагов:

1. **Шаг «Параметры токена»** (как сейчас): выбор узла, крипта, сумма, сеть (если нужно), отображаемый email (первый из настроенных).  
2. **Шаг «Подтверждение по email»**  
   - Кнопка «Отправить код».  
   - Вызов API `request-verification-code` с выбранным email.  
   - После успеха: текст «Код отправлен на {email}. Проверяем почту…» и запуск фонового сканирования (INBOX, затем Spam, Junk и т.д.).  
3. **Поведение при сканировании**  
   - Индикатор загрузки / «Проверяем папку Входящие…», «Проверяем папку Спам…» (опционально).  
   - Если код найден — автоматически перейти к шагу 4 с подставленным кодом.  
   - Если код не найден в течение N минут — показать поле «Введите код вручную» + кнопка «Проверить» / «Создать токен».  
4. **Шаг «Создать токен»**  
   - Поле ввода кода (заполняется автоматически, если код найден, иначе пользователь вводит).  
   - Кнопка «Создать токен».  
   - Запрос `create` с телом, включающим `verification_code`.  
   - Обработка успеха/ошибки как сейчас (сохранение токена, переход назад и т.д.).

Альтернатива: не показывать отдельный «шаг ввода кода», а после «Отправить код» сразу показывать экран с индикатором и полем «Код» внизу; при авто-обнаружении подставлять код и разрешать нажатие «Создать».

### 4.5. Обработка ошибок

- Нет настроенных email → сообщение «Добавьте и подключите email в Настройках».  
- request-verification-code вернул 429/400 → показать сообщение с сервера.  
- Не удалось подключиться к почте (IMAP/POP) → «Не удалось проверить почту. Введите код вручную».  
- Папка Spam недоступна (например POP3) → сканируем только INBOX, при отсутствии кода — подсказка «Проверьте папку Спам вручную».  
- Код истёк (API вернул ошибку при create) → «Код устарел. Запросите новый».

## 5. Зависимости и порядок реализации

1. **API**  
   - Конфиг/кэш: TTL кода (например 30 мин).  
   - Маршрут POST `request-verification-code`, контроллер: генерация кода, кэш, отправка Laravel Mail (`MailboxVerificationCodeMail`, Blade `mailbox_verification_code_layout` + plain). При отсутствии фрагментов от клиента — фиксированный English fallback в Mailable.  
   - В `EscrowTokenController::create`: проверка `verification_code` из body, сверка с кэшем по email, при успехе — вызов Core и удаление кода из кэша.

2. **Клиент — слой данных**  
   - RemoteDataSource: метод `requestEscrowVerificationCode(apiUrl, email): Result<Unit>`.  
   - RemoteDataSource/createEscrowToken: добавить параметр `verificationCode: String?` и передавать в теле запроса.  
   - ClientEmailReader: расширить контракт (folderName в getEmailList и при необходимости в getRawEmail).  
   - JavaMailClientEmailReader: реализация работы с произвольной папкой по имени; при отсутствии папки — корректная ошибка/пустой список.

3. **Клиент — слой приложения**  
   - Use case или логика в EscrowTokenViewModel: запрос кода → сканирование папок (INBOX, Spam, Junk, …) в цикле с задержкой между попытками → парсинг кода из писем → вызов create с кодом.  
   - Состояния UI: Idle, RequestingCode, ScanningMailbox, CodeFound, WaitingManualCode, Creating, Success, Error.

4. **Клиент — UI**  
   - Экран создания токена: добавить шаг «Отправить код» и блок «Проверяем почту» с возможностью ручного ввода кода и кнопкой «Создать токен».

5. **Шаблон письма**  
   - HTML в стилистике deal notification (`mailbox_verification_code_layout.blade.php`) + plain text (`mailbox_verification_code_plain.blade.php`). Числовой код на своей строке для парсинга в клиенте.

## 6. Laravel host и поле `core_base_url`

Код подтверждения живёт в кэше **конкретного** экземпляра Laravel. Поэтому **и** `POST …/request-verification-code`, **и** `POST …/escrow-tokens/create` с тем же `verification_code` должны попадать **в тот же** нормализованный базис **`…/api/v1`** этого инстанса. Поле тела **`core_base_url`** при create проверяется по allowlist из **`nodes.endpoints` (`core_*`, `core_api`) активных узлов этой же БД** (`App\Services\EscrowTokenService`): значение должно канонически совпасть с одним из них.

Клиент (**xboard-client**), подробнее: `docs/ESCROW_TOKEN_SYSTEM.md` (*Laravel `/api/v1` minting URL vs Core base*).

- **Пакет**: один общий Laravel-базис; Core отдельно на каждый узел из строки узла (`NodeEscrowEndpoints`).
- **Один токен при фильтре по домену стороннего узла** (`escrow_node_domain_filter_*`): Laravel как у потока с «базового» ref приложения (**`normalize(refDataBaseUrl)`**); Core из **`core_*`** выбранного узла.
- Экран узла (**`EscrowTokensSection`**): отправка кода и create через тот же **нормализованный ref** базис приложения (`escrowMintingApiV1Base`).

## 7. Итоговая схема потока

```
[Пользователь] → Выбор параметров токена, email = первый из настроенных
       ↓
[Клиент] → POST /v1/escrow-tokens/request-verification-code { email }
       ↓
[API] → Генерация кода, кэш (email → code, TTL 30 мин), отправка письма на email
       ↓
[Клиент] → Сканирование INBOX, затем Spam, Junk, … (встроенный IMAP)
       ↓
[Клиент] → Поиск кода в теме/теле писем (регулярное выражение)
       ↓
       ├─ Код найден → подставить в форму, кнопка «Создать токен»
       └─ Не найден (таймаут) → поле «Введите код вручную» + «Создать токен»
       ↓
[Клиент] → POST /v1/escrow-tokens/create { ..., verification_code: "123456" }
       ↓
[API] → Проверка кода по email в кэше, при совпадении — создание токена в Core, удаление кода из кэша
       ↓
[Клиент] → Сохранение токена, переход назад / обновление списка
```

---

Документ можно использовать как основу для реализации и уточнения деталей (имена папок, формат кода, точные тексты ошибок).
