## XBoard: чек-лист безопасности и устойчивости деплоя

Этот документ — задание на проверку/аудит для всей связки:

- `xboard-client` (Android‑клиент);
- `xboard-api` (Laravel API);
- `xboard-core` (PHP‑ядро);
- `xboard-monero-balance` (Go‑сервис балансов/трансферов);
- почтовый сервер `mail.xdexboard.com` (`server@xrpchange.site`, Postfix + Dovecot).

Цель: **выявить и закрыть стандартные векторы атак** (забивание диска, brute‑force, злоупотребление API и т.п.) на реальных деплоях.

---

### 1. Заполнение диска / ресурсоёмкие атаки

- **Логи и очереди**
  - Mail / Postfix:
    - проверить ротацию и лимиты для `/var/log/mail.log`;
    - учесть настройки `maximal_queue_lifetime`, `bounce_queue_lifetime`, `mailbox_size_limit`;
    - убедиться, что очередь Postfix не может расти бесконечно при сбое доставки.
  - API / PHP:
    - проверить ротацию `storage/logs/laravel.log` и любых кастомных логов в `xboard-api` и `xboard-core`;
    - убедиться, что размер логов ограничен (rotate, compress, max size).
  - Monero‑balance:
    - проверить ротацию логов balance‑сервиса;
    - убедиться, что база/история транзакций не растёт без лимитов (есть TTL/архивация).

- **IMAP‑хранилище**
  - Проверить, что связка `doveadm expunge/purge` + `mailbox_size_limit` реально исключает сценарий, когда злоумышленник забивает диски письмами (в т.ч. по IMAP).
  - Убедиться, что нет отдельных «архивных» папок, которые не попадают под регулярную очистку.

- **Файлы и вложения (xboard-api)**
  - Проверить каталоги `storage/app`, временные файлы чеков, экспортов, скринов:
    - есть ли TTL/очистка для временных файлов;
    - есть ли ограничения по размеру/количеству файлов;
    - нет ли сценария, при котором злоумышленник может массово заливать бесполезные файлы.

---

### 2. SMTP / IMAP / почтовый слой

- **Postfix**
  - Верифицировать, что **нет способов обойти `smtpd_sender_login_maps`**:
    - через `submission` / `submissions`;
    - через локальный `sendmail`;
    - через relay на внешние домены.
  - Проверить и, при необходимости, задать лимиты:
    - `smtpd_client_connection_count_limit`;
    - `smtpd_client_connection_rate_limit`;
    - `smtpd_client_message_rate_limit`;
    - `anvil_rate_time_unit`.

- **Dovecot / IMAP**
  - Проверить политику паролей ящиков (особенно `check@xdexboard.com` и ящики лотов):
    - минимальная длина;
    - сложность;
    - отсутствие общих/известных паролей.
  - Проверить лимиты сессий/логинов:
    - ограничения по количеству одновременных соединений с одного IP;
    - защита от brute‑force (fail2ban / встроенные лимиты).

- **Email → чат (клиент)**
  - Подтвердить, что содержимое писем, уходящее в чат клиента:
    - **никогда не рендерится как HTML/JS**, только как безопасный plain text;
    - не может содержать активный контент (скрипты, произвольный HTML).

---

### 3. HTTP API (xboard-api, xboard-core)

- **Rate limiting и abuse**
  - Наложить/проверить лимиты (per IP / per токен / per устройство) на:
    - регистрацию/логин/валидацию почты;
    - операции чата (`sendMessageToBuyer` / `sendMessageToSeller`, `markChatCleared`);
    - создание/обновление лотов и сделок;
    - монеро‑связанные HTTP endpoints (через core/balance‑service).
  - Проверить, что rate limiting не даёт злоумышленнику:
    - массово спамить валидацию/кодами;
    - создавать/обновлять тысячи лотов/сделок за короткое время.

- **Размеры и формат payload**
  - Задать и протестировать чёткие max‑лимиты по:
    - длине сообщений чата;
    - размеру и содержимому заголовков `X-XBoard-Deal-Tag`;
    - размеру JSON‑тел (например, `POST /exchange-lots/...` и другие ключевые endpoints).
  - На текущем деплое уже добавлены **лимиты в БД для сообщений чата** (максимальная длина текста / ограничения истории);
    при аудите нужно сверить, что они совпадают с целевыми значениями и покрыты тестами.
  - Проверить корректность обработки:
    - очень длинных строк;
    - бинарного мусора;
    - некорректного JSON (ошибки должны быть контролируемыми, без падений/утечек стека).

- **Auth / ACL**
  - Убедиться, что:
    - нет оставшихся debug/test endpoints без аутентификации;
    - нельзя читать/менять чужие сделки/чаты простым подбором ID (IDOR):
      - все чувствительные операции жестко проверяют владельца/роль/сторону сделки.

---

### 4. Android‑клиент (xboard-client)

- **Работа с почтой/чатом**
  - Убедиться, что клиент не может быть использован как SMTP‑ретранслятор:
    - нет прямых SMTP‑подключений из клиента к внешним серверам;
    - вся почта идёт только через backend `xboard-api`.
  - Проверить устойчивость к «грязным» входящим письмам:
    - очень длинные заголовки;
    - бинарный мусор в теле;
    - нестандартные кодировки;
    - результат — не должен приводить к крашу/ANR.

- **Безопасность UI и данных**
  - Проверить, что:
    - нет хранения чувствительных данных (токены, e‑mail‑логины, пароли) в plaintext (SharedPreferences/файлы/лог);
    - глубокие ссылки из писем/уведомлений не могут открыть «чужую» сделку:
      - при открытии по deeplink обязательно проверяется авторизация и право доступа к конкретному `lot_id`/`deal_id`;
      - любые ошибки отображаются безопасно, без утечек деталей.

---

### 5. Monero‑balance сервис (xboard-monero-balance)

- **HTTP интерфейс**
  - Проверить:
    - наличие и проверку auth‑ключа для `/transfer`, `/balance` и прочих endpoints;
    - IP‑ограничения (кто вообще может дергать API balance‑сервиса);
    - применение rate limiting (чтобы нельзя было зафлудить сервис).

- **Ресурсные атаки**
  - Проверить, что нет простого способа:
    - загнать сервис в CPU/IO‑100% длинными/частыми запросами;
    - раздуть базу (миллионы фейковых токенов / history entries) без cleanup/TTL.
  - Убедиться, что:
    - есть мониторинг основных метрик (CPU, память, размер БД, время ответа);
    - есть план реагирования при выходе за пороги.

---

### 6. SSH / окружение сервера

- **SSH защита**
  - Проверить, что:
    - вход по SSH только по ключам (пароли выключены);
    - root по SSH запрещён (работа через пользователя `server` + `sudo`);
    - есть защита от брутфорса (fail2ban / аналог) по SSH;
    - при необходимости есть защита по SMTP/IMAP (ограничения по IP/скорости).

- **Права на служебные скрипты**
  - Проверить владельца и права:
    - `/usr/local/bin/renew_cert.sh`;
    - `scripts/email-server/check_rbl_blocks.py`;
    - других maintenance‑скриптов.
  - Убедиться, что:
    - обычные пользователи не могут редактировать эти скрипты;
    - скрипты лежат в ожидаемых местах и вызываются только из доверимых контекстов (cron, systemd).

---

Этот чек‑лист можно использовать:

- как задание для внешнего аудита/модели (Grok и т.п.), чтобы получить подробный план и сценарии тестирования по каждому пункту;
- как внутренний план обхода прод‑деплоя: фиксировать конкретные конфиги, логи и результаты для каждого подпункта.
